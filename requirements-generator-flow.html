Requirements Generator — System Flowchart

How the slash commands fit together. Every engagement passes through three required steps: drop the client's material into documentation/, run /requirements to turn it into a spec, and run /export-requirements to hand that spec over for development. Everything else is optional — commands that check or deepen the inputs and the spec (reviews, analyses, amendments), and commands that produce extra deliverables (a PRD, wireframes, a clickable prototype). Two commands sit outside that flow: /design-system runs independently, any time, and /ingest-stadium is only for clients who hand you a Stadium 6 app. Before your first engagement, run /setup once per machine. /start lists every command and launches the one you pick. §2Reviews vs Analyses — purpose at a glance

Both optional pipeline families lens the same source material (raw documentation/ or merged requirements-prototype.md), but they produce categorically different outputs and demand different consultant actions.

Reviews

Critique — what is wrong with the source

Purpose
Surface defects, gaps, ambiguities, contradictions, completeness holes, and risks in the source material.
Output shape
A punch-list of findings — never an auto-patch. The artefact is something the consultant reads and acts on, not a positive contract for downstream tools.
Consultant action
Manual edits to documentation/ files (for /review-inputs) or to requirements-prototype.md (for /review-requirement). Some findings also generate follow-up elicitation questions for the client.
Pick when
You suspect the source is incomplete, ambiguous, or weak, and you want a structured list of specifically what to fix before drafting or designing further.
Examples
adversarial · completeness-review · ambiguity-review · first-principles · ten-ba-questions · ten-ux-questions · user-stories · gap-analysis · requirements-quality · requirements-traceability

Analyses

Transform — make implicit structure explicit

Purpose
Derive a structural model (objects, jobs, journeys, tasks, themes, state lifecycles, …) from the source so downstream design phases can key off an explicit contract instead of improvising.
Output shape
A positive artefact — object map, theme map, task tree, journey card, state diagram, opportunity-solution tree — that another pipeline can consume as input.
Consultant action
Choose Accept & use to write a compact re-ingestion extract into documentation/ for the next /requirements pass (for /analyse-inputs), or for /analyse-requirement — select it as an input to /wireframe.
Pick when
You want to enrich the source with a structural lens (motivation, object model, process flow, sentiment journey) before drafting or designing — and you want that lens to flow forward as a positive contract.
Examples
ooux · jtbd · journey-mapping · task-analysis · opportunity-solution-trees · state-diagram · data-model · use-cases · thematic-analysis · affinity-mapping · mvp-slicing · crud-coverage · decision-tables · faceted-classification · glossary · user-goal-analysis · business-context-definition

§3How outputs flow back into inputs

Pipeline outputs are not auto-piped. The consultant manually shuttles relevant pieces between runs — every cross-pipeline transfer is an explicit decision with a paper trail.

The handoff patterns

FromWhat the consultant does with the output
/generate-prd Copy strategic content (success metrics, MVP phasing, hypotheses) into documentation/ before running /requirements.
/analyse-inputs · any methodology At the end of each analysis choose Accept & use: it writes a compact Markdown re-ingestion extract (documentation/<method>.analysis.md) that /requirements reads on its next run. Plain Accept keeps the analysis for reading only.
/review-inputs · any methodology Read the punch-list and manually edit the source files in documentation/ — add missing context, resolve ambiguity, surface stakeholder voices. Then re-run /requirements against the improved corpus.
/review-requirement · any methodology Read the punch-list and manually edit generated-docs/requirements/requirements-prototype.md to address defects — or re-run /requirements with corrective input. The review never auto-patches the spec.
/resolve-review The assisted alternative to hand-editing after a review: pick an existing review artefact (generated-docs/review-inputs/ or generated-docs/review-requirements/), select the findings to act on, and resolve each one interactively — every AI-inferred resolution is confirmed by an explicit affirmative, either per finding or in one go via an explicit Accept all remaining as drafted choice (nothing is silently assumed). The approved resolutions are written as a new dated document into documentation/ (never overwriting an existing file), ready for the next /requirements run. Review-requirements-sourced runs can additionally (opt-in) cache the same resolutions as a transient Amendments section in requirements-prototype.md until the next re-merge folds them in.
Select relevant analyses (OOUX object map, user-journeys, task-flows, trade-off-dimension matrix) as supporting inputs when you run /wireframe (Stage 1b — completed analyses are read sidecar-first) or /prototype (basis B of its A–E input selection), so the produced screens and prototype reflect the lensed structure. They also remain reference reading you use to set scope and trade-off-dimension positions.

/setup

Your machine → ready to run every command
Inputs
None. Optionally a component name — e.g. /setup core for the core dependencies only, or /setup inkscape / /setup libreoffice for the rarely-needed .svg / .vsdx renderers. No argument installs everything.
When to use
Before your first engagement on a machine. Also once in every new copy of the workspace — the artefact-preview check (HTML outputs opening in your browser before you accept them) belongs to the workspace, not the machine. Safe to re-run: anything already installed is checked and left alone.
Delivers
The tools the commands need — markitdown (Office and PDF inputs), Node, draw.io, Playwright (/design-system URL extraction and /prototype checks) — plus a status table with one ✅ / ⚠️ / ❌ row per dependency. Writes no requirement artefacts.
How to use
Run it and read the table. If any row shows ⚠️, restart Claude Code and run /setup again — newly installed tools only become usable after a restart. A ❌ row names its own repair.
/ingest-stadium Base · pre-requirements · input preparation
↑ Back to paths

/ingest-stadium

Stadium 6 app → citation-ready input assets
Inputs
A Stadium 6 application dropped in documentation/ — a deployed app folder (administration.db + App_Data/Updates/*.sapz + ClientApp/) or a one-line *.stadium pointer naming its path. Runs a bundled, standard-library-only Python extractor.
When to use
First, whenever the client's material is a Stadium low-code app rather than (or alongside) documents. Extraction happens once per app — a process-once ledger skips an already-ingested app unless you deliberately re-ingest via the prompt, so your hand-edits to the assets are never silently overwritten.
Delivers
documentation/<AppName>.stadium-assets/ — thirteen lean, citation-ready assets (eleven deterministic category files: overview, data model, data sources, business rules, access control, surfaces, user tasks, navigation, glossary, design signals, modules; plus two advisory [AI-SUGGESTED] ones: task flows, quality signals). A forensic model.json lands under framework/state/ and is never manifested.
How to use
Nothing further — the assets are ordinary Native-text inputs. The next /requirements (or /generate-prd / /analyse-inputs / /review-inputs) run enumerates them automatically; those commands exclude the raw app folder and nudge you here if they spot an un-ingested app.
documentation/ Required · intake · input drop folder
↑ Back to paths

documentation/

The client's material — not a command, a folder
Inputs
Whatever the client hands over: briefs, decks, screenshots, spreadsheets, PDFs, diagrams. Text (.md, .txt, .yml, .yaml, .xml) and images (.png, .jpg, .jpeg, .gif, .webp) are read directly; Office and PDF (.docx, .xlsx, .pptx, .pdf) are converted first; diagrams (.drawio, .svg, .vsdx) are rendered and described. Anything else is logged so it doesn't slip through silently.
When to use
Always, first — after /ingest-stadium if the client gave you a Stadium 6 app. Add more files at any point; the next run of an input command picks them up.
Delivers
Nothing by itself — it is the drop zone that /requirements, /generate-prd, /analyse-inputs and /review-inputs read. The files are yours: the framework never modifies or deletes them.
How to use
Drop the files in, then run /requirements (or any of the optional input commands first). Outputs from /resolve-review and /amend-requirements land here as new dated files, and you can copy PRD or input-analysis content in by hand — see §3.
/review-inputs Optional · pre-requirements · 6 methodologies
↑ Back to paths

Common to all 6 methods

Critique the raw documentation/ material for missing context, ambiguity, contradiction and gaps in the stakeholder voice.

Reads
Every file in documentation/
Results
A list of findings in generated-docs/review-inputs/<METHOD>/. Never changes your files.
Usual next step
Ask the client the questions it raises, or edit the files in documentation/ yourself. Or run /resolve-review to turn chosen findings into a new approved input document. Then re-run /requirements.

adversarial

Where does the material contradict itself, miss voices, or stay silent?

Reveals
Roles and workflows nobody describes, sources that contradict each other, vague wording, missing numbers and unclear scope.
You learn
Each defect, rated by how much it matters for the frontend spec, with a recommendation for handling the material you already have.
Improves
The draft starts from material whose weaknesses are already handled, so fewer contradictions and guesses reach the spec.
BMAD-style adversarial critique · ADVERSARIAL/adversarial-review.html

completeness-review

What does the material miss by professional business-analysis standards?

Reveals
Areas the material leaves uncovered, measured across ten coverage dimensions against standard BA practice, not this project's template.
You learn
Each gap and whether it needs the client, is covered by a standard rule, or is out of scope; plus ready-to-ask questions per source.
Improves
Answers to the questions become new inputs, so the spec rests on client facts, not guessed values.
IEEE 29148, Volere, BABOK, Wiegers, INCOSE, ISO 25010 · COMPLETENESS-REVIEW/completeness-review.html

ambiguity-review

Which statements could two people read differently?

Reveals
Vague verbs, weak "should/may", undefined "it/they": wording the drafter would otherwise interpret silently.
You learn
Each ambiguous phrase, its competing readings, and a client question ready to send.
Improves
Fewer guessed rules in the spec; acceptance criteria that can actually be tested.
Berry/Kamsties + Femmer · AMBIGUITY-REVIEW/ambiguity-review.html

gap-analysis

Drop into documentation/

Which sections of the spec will the material leave empty?

Reveals
Parts of this project's requirements template the material leaves empty or thin, before the drafter has to fill them with guesses.
You learn
A coverage heatmap, each gap prioritised must/should/could/won't, and a ready-drafted "the system shall …" requirement for every must or should gap.
Improves
Ratify, edit or reject the candidates and drop the file into documentation/; the next /requirements run cites the ones you keep.
Gap analysis against the requirements template, MoSCoW priorities · GAP-ANALYSIS/gap-analysis.html

ten-ba-questions

Which ten business questions should I ask the client first?

Reveals
The business gaps that matter most (scope, rules, data ownership), named rather than buried in an exhaustive audit.
You learn
Ten stakeholder questions ranked by business impact, how poorly the material answers them, and how many others each unblocks. Each cites a source file or is marked absent.
Improves
Answers settle scope, rules and data ownership before drafting, so the spec carries fewer open questions.
Eight BA gap categories · TEN-BA-QUESTIONS/ten-ba-questions-review.html

ten-ux-questions

Which ten design questions should I ask users and stakeholders first?

Reveals
The design gaps that matter most: who the users are, where they work, how they decide, recover from errors and collaborate.
You learn
Ten design questions ranked by design impact, how poorly the material answers them, and how many others each unblocks. Each cites a source file or is marked absent.
Improves
Answers give the spec real user groups, decision points and error cases, so screens are designed from evidence, not assumption.
Eight UX gap categories · TEN-UX-QUESTIONS/ten-ux-questions-review.html

task-analysis

How exactly do users get each task done, step by step?

Reveals
The sub-steps, branches and repeats inside each task, and the data every step reads or writes.
You learn
A numbered tree of goals, sub-goals and operations, with a plan on every branch saying in what order or under what condition steps run.
Improves
The drafter uses the tree as a completeness target: plans become acceptance-criteria branches, step data seeds §7 data shapes.
Hierarchical Task Analysis (Annett & Duncan) · TASK-ANALYSIS/task-analysis.html

thematic-analysis

What patterns keep coming up across the interviews and notes?

Reveals
Recurring patterns across unstructured interviews, notes and decks that no single source states outright.
You learn
The themes and the coded passages behind them, a theme map, and candidate requirements bridged from each theme.
Improves
/requirements drafts from the themes and picks up the candidate requirements like any other source.
Braun & Clarke six-phase · THEMATIC-ANALYSIS/thematic-analysis.html

opportunity-solution-trees

Which options reach the client's outcome, and which assumptions need testing?

Reveals
The opportunities and alternative solutions behind a stated outcome, before requirements lock in one feature set.
You learn
A tree from outcome to opportunities, solutions and the assumption tests that show what to validate first.
Improves
The next /requirements draft seeds its scope from the candidate requirements, before a feature set is locked in.
Teresa Torres (2016) · OPPORTUNITY-SOLUTION-TREES/opportunity-solution-tree.html

journey-mapping

What does today's workflow feel like for each type of user?

Reveals
Where today's workflow hurts each persona: pain points, touchpoints and the low moments along the way.
You learn
One journey card per persona: phases, steps, touchpoints, channels, a sentiment curve, pain points and opportunities.
Improves
Gives the draft a backbone for §5 task flows, integrations and §4.2 user stories; pain points help set priorities.
NN/g + Kalbach current-state journey · JOURNEY-MAPPING/journey-mapping.html

jtbd

Why do users act, and which of their needs are least served?

Reveals
The motivation the inputs imply but never name: the jobs users need done and what pushes them forward or holds them back.
You learn
A job map with outcomes, the push, pull, anxiety and habit forces, and opportunity scores showing which jobs are most underserved.
Improves
The draft targets jobs and outcomes rather than features: jobs become in-scope items, forces become design context.
Christensen-Moesta + Ulwick · JTBD/jtbd-job-map.html

ooux

What are the main objects, and which names mean the same one?

Reveals
Synonyms across sources (Customer, Client, Account holder) that are really one object, plus relationships and actions the inputs only imply.
You learn
One reconciled object model: each object with its attributes, relationships and actions, tagged by source, plus a log of every synonym merge.
Improves
/requirements takes the whole object model in one pass, so §7 data shapes use one name per object.
Sophia Prater's ORCA · OOUX/ooux-object-map.html

swim-lane-process-mapping

Where does work get stuck when it passes between people or teams?

Reveals
Broken handoffs between roles: the gaps between teams where processes most often fail.
You learn
A swim-lane flowchart per process, an actor list, and a register classing every handoff as clean or one of four disconnect types.
Improves
Processes seed §5 task flows; handoffs seed integration constraints; decisions seed acceptance-criteria branches; data stores seed §7 data shapes.
Rummler-Brache + disconnect analysis · SWIM-LANE-PROCESS-MAPPING/swim-lane-process-mapping.html

affinity-mapping

What groups emerge from this pile of notes, without forcing a structure?

Reveals
Themes hiding in a large, messy pile of notes, plus the notes that fit nowhere and the tensions between clusters.
You learn
Notes grouped bottom-up into labelled clusters and 4–8 super-themes, with a confidence mark per cluster and the orphans and tensions listed.
Improves
Super-themes anchor the §1 application context, clusters group §5 task flows, orphans become out-of-scope candidates (§1.5), tensions become trade-off-aware criteria.
Kawakita KJ + Beyer/Holtzblatt · AFFINITY-MAPPING/affinity-map.html

glossary

Do we all mean the same thing by the key terms?

Reveals
Terms the inputs leave undefined, use weakly, give synonyms for, or define in conflicting ways.
You learn
Each significant term, classed domain or application, with its cited definition, how settled it is (0–4), and a proposed definition where the inputs fall short.
Improves
/requirements adopts the agreed terms as canonical vocabulary, so the spec uses one word per concept.
Ubiquitous-language vocabulary · reads the inputs, unlike the /analyse-requirement glossary · GLOSSARY/glossary.html

user-goal-analysis

What are the users actually trying to achieve, stated or implied?

Reveals
Goals behind the request that the inputs only imply, and goals of different actors that conflict.
You learn
A goal register grouped by goal type, an AND/OR refinement tree, an actor map and a conflicts table; inferred goals are flagged.
Improves
Explicit goals seed §4.2 user stories; inferred goals reach the spec only if you confirm them.
Goal-oriented requirements engineering (GORE) · USER-GOAL-ANALYSIS/user-goal-analysis.html

business-context-definition

What business problem is this solving, and why does it matter?

Reveals
The enterprise motivation behind the request: the business problems, needs and goals, not individual users' goals.
You learn
One causal chain from business problem to need, goal and problem statement, with inferred items flagged for confirmation.
Improves
The chain seeds the strategic framing of the next draft, so requirements trace back to a business problem.
BMM + BABOK · pairs with user-goal-analysis · BUSINESS-CONTEXT-DEFINITION/business-context-definition.html

/resolve-review

Review findings → approved input document
Inputs
One existing review artefact, picked from disk — any generated-docs/review-inputs/<METHOD>/ or generated-docs/review-requirements/<METHOD>/ output. Run a review first.
When to use
After a review, when you want its findings acted on rather than just listed — the assisted alternative to hand-editing documentation/ files or requirements-prototype.md. You select which findings to address and resolve each one in turn; every AI-inferred resolution is confirmed by an explicit affirmative — per finding, or in one go via an explicit Accept all remaining as drafted choice — before it is recorded.
Delivers
One new dated resolutions document under documentation/ per run — existing input files are never modified or overwritten. Each resolution is origin-marked (consultant-stated vs AI-inferred-and-confirmed) and carries a Supersedes line so cross-source-conflict detection stays honest. On review-requirements-sourced runs you can additionally opt in to a transient Amendments (pending re-merge) section cached inside requirements-prototype.md for immediate downstream use.
How to use
Re-run /requirements — the resolutions document is picked up like any other input file and your decisions are folded into the regenerated spec (which also clears the transient Amendments cache). One run resolves one review; re-invoke for another.

/amend-requirements

Inputs

When to use
The spec is written and you already know what to change — no review involved. Reachable directly, or as the amend option when you re-run /requirements on a finished spec.
Delivers
A new documentation/amendments-<date>.md — the durable record, folded into the spec body with citations by the next /requirements run — and a transient ## Amendments (pending re-merge) section inside requirements-prototype.md, so /wireframe, /prototype, the analyses and /export-requirements honour the change immediately. Nothing existing in documentation/ is overwritten and no other line of the spec is touched.
How to use
A specific change is recorded as you stated it; a change that is only a direction ("tighten up approvals on rate changes") comes back as two or three concrete alternatives with their consequences, and you pick one. You are also told what the change affects — data properties the wireframes bind to, the scope boundary, and which wireframes or exports were built against the older spec.

/wireframe

Parallel low-fi HTML variants
Inputs
generated-docs/requirements/requirements-prototype.md (full, scoped via the scope-selector at Stage 1). Reads framework/assets/pattern-catalogue/** for pattern bindings. Optionally reads the trade-off-dimension analysis as an architect applicability input.
When to use
After requirements-prototype.md is accepted (and ideally after any requirement reviews/analyses you wanted to run), to explore divergent UX positions on a scoped slice. Two variants default; up to three for richer comparisons.
Delivers
wireframes/<scope>/index.html (metadata landing — scope, side-by-side variant columns of new-tab screen links, prose cards, trade-off matrix). Per-variant screen HTMLs with data-src requirement-ID traceability and data-prop property traceability.
How to use
Open two variants' screens side-by-side via browser tab-drag (the index links every screen as target="_blank"). Use the trade-off matrix and prose cards to drive variant selection with the client; then hand the chosen variant to /prototype as its wireframe basis (basis D), or feed selected directions back as constraints for the next requirements pass.

The final, highest-fidelity step. Each run produces one clickable, client-side-only React/Next.js prototype of a scope of requirements-prototype.md, accumulating in one shared app under prototypes/ (scaffolded once from template/) reachable from a single landing page. Look & feel is brand-locked and identical across every prototype — divergence is pure UX: a named UX posture + trade-off positions (D1–D5) reshape layout and workflows. Shares the scope-selector skill and blueprint-architect agent with /wireframe.

/prototype

Hi-fi clickable prototype (one shared app)
Inputs
generated-docs/requirements/requirements-prototype.md (scoped via the shared scope-selector) + your A–E supporting-input selection — A requirement, B generated-docs/analyse-requirements/*, C generated-docs/analyse-inputs/*, D wireframes/<scope>/*, E documentation/* — plus generated-docs/design-system/design-system.html (or the previous per-mode files) for brand (if present; else reference-URL / paste-tokens / template defaults) and template/ as the one-time scaffold source.
When to use
After requirements-prototype.md is accepted and wireframes have settled a direction, when you want a clickable artefact to demo with the client. Run it again — different posture or positions, same brand — to add a divergent prototype for side-by-side comparison.
Delivers
prototypes/ — one shared Next.js app: a landing page listing every prototype grouped by scope, a per-run prototype under src/app/<name-slug>/, shared components / fixtures / one theme.css, and a PrototypeChrome with a role switcher (PI-05) + data reset. Every data-bound element is traceable to a blueprint Property closed set (anti-fabrication); the build is verified (lint + typecheck + build + Playwright smoke) and honours invariants PI-01..PI-08.
How to use
Pipeline per run: scope + name → A–E inputs → blueprint (reused if present) → purpose + posture + positions → design-spec draft → resolve → merge → scaffold-if-needed → parallel per-surface generation → verify → landing update. Open the landing page, click into the prototype, and walk the client through the workflow. Designating a /wireframe variant as the basis pre-fills the posture and D1–D5 positions from that variant.

/export-requirements

Application-audience re-projection of the spec
Inputs
generated-docs/requirements/requirements-prototype.md — sole content input, exported as it exists at that moment, amendments included. Pending amendments are first folded into the export's copy of the body, with every edit listed in fold-report.md for you to check at the gate. Apart from that fold, nothing is invented at export time — the only export-supplied wording is a small fixed set of replacements. requirements-prototype.md is never changed.
When to use
Once the requirements have settled — after the analyses, reviews, wireframes, and manual refinements have shaped the spec into what you actually want built — and a dev team outside this workspace needs the build-ready version.
Delivers
generated-docs/export-requirements/requirements-application.md (plus fold-report.md when amendments were folded; an amendment whose anchor can't be found stops the run before any write) — amendments folded into the body, prototype-only scaffolding stripped (the prototype-invariants appendix and the framework-internal target-mode table), fixture references rebased to backend-contract pointers, the prototype-scoping preamble dropped from the guidance sections, and a provenance block stamped in with a sha256 fingerprint of the exact source version, so a re-run can tell you whether the export is stale. Anything that can't be cleanly re-projected — a prototype-flavoured phrase inside a cited requirement, say — is left exactly as written and flagged in the provenance block and under the affected section, rather than quietly reworded. Self-describing for external readers via a citation legend.
How to use
Hand it over together with generated-docs/requirements/draft-claims.ndjson (the verbatim source quotes behind the citation tags). Re-running after the spec changes offers a one-click regenerate; the prior export is checkpointed to git first.
